# 个人信息安全事件应急预案(泄露响应)

> 生成:2026-08-15 | 版本:1.0 | 适用范围:叙阅产品与服务(含数据库、AI 出站、接口、前端)
> 对接依据:《个人信息保护法》第 57 条(泄露通知义务)、《数据安全法》第 22 条(应急处置)、《网络安全法》第 25 条(安全事件应急)、《GB/T 35273-2020 个人信息安全规范》第 10 章(安全事件处置)
> 衔接现有合规能力:2B 访问留痕(access_logs)+ 年度审计导出、2C 成绩等级制、2D AI 标识、2E AI 管控、2F 数据分类分级清单

---

## 1. 总则

### 1.1 目的

建立叙阅个人信息安全事件(尤其是数据泄露)的**分级、报告、处置、通知、复盘**完整闭环,确保:

- 事件第一时间发现、上报、止损
- 依法履行《个人信息保护法》第 57 条的通知义务
- 证据保全满足后续追责与监管调查要求
- 事后复盘补漏,防止同类事件复发

### 1.2 依据(节选)

| 法条            | 要求                                                                           | 对叙阅的含义                         |
| --------------- | ------------------------------------------------------------------------------ | -------------------------------------- |
| PIPL 57         | 泄露/篡改/丢失应立即补救 + 通知网信部门和主管监管部门 + 危害无法根除须告知个人 | 泄露须向监管报告;影响家长/学生须告知   |
| 数据安全法 22   | 数据安全事件立即处置、及时向网信部门报告                                       | 教育数据(学籍/成绩/健康)属重点保护对象 |
| 网络安全法 25   | 制定网络安全事件应急预案                                                       | 需有文档化预案 + 演练                  |
| GB/T 35273 10.1 | 应急预案、应急响应组织、处置流程                                               | 落地到具体角色与步骤                   |

### 1.3 涉及的数据资产(衔接 `docs/contracts/13-data-classification.md`)

- **L4-L5 敏感数据**:学籍号、手机号、家长电话、家庭住址、成绩/等级、健康信息(晨午检)、测评结果、成长画像
- **AI 出站**:AI 评语/诊断/报告调用第三方模型(已做匿名化 + 掩码,见 2D/2E/2F)
- **账号数据**:users/profiles(邮箱/手机)、行权导出(CSV 含全字段)

## 2. 事件分级

按「涉及数据级别 × 影响范围 × 可预测损害」三分级:

| 级别           | 判定标准                                                                             | 示例                                                     | 响应时效                               |
| -------------- | ------------------------------------------------------------------------------------ | -------------------------------------------------------- | -------------------------------------- |
| **一级(一般)** | 仅 L2-L3 数据泄露;影响单个班级/少量记录;无实质损害                                   | 单条学籍号误发、单个账号异常                             | 24h 内处置闭环                         |
| **二级(较大)** | 涉及 L4 数据(成绩/健康/手机/住址);影响 1-2 个班或批量记录;或 AI 出站疑似泄漏敏感字段 | 班级名单含家长电话被导出外泄、健康明细批量流出           | 4h 内上报、24h 内初步处置              |
| **三级(严重)** | 涉及 L4-L5 大批量泄露(跨校/全量);疑似外部攻击;或涉及未成年人敏感信息规模泄露         | 数据库被拖库、CSV 全字段行权导出外泄、评测结果大规模流出 | **立即**(1h 内)启动应急 + 监管通报准备 |

> 未成年人信息从严:涉及未成年学生信息的泄露,一律按**上浮一级**处理(《未成年人保护法》第七十二条精神)。

## 3. 应急组织与职责

| 角色                              | 职责                                               |
| --------------------------------- | -------------------------------------------------- |
| **应急总指挥**(负责人/CTO 或指定) | 事件定级、启动响应、对外/监管决策、资源调配        |
| **技术处置组**(后端/运维)         | 隔离止损、定位根因、修复、证据保全                 |
| **合规对接人**(法务/合规)         | 判定法定义务、起草监管通报与个人告知文案、协调律师 |
| **用户沟通组**(客服/产品)         | 内部渠道(学校/老师)沟通口径、答疑、情绪安抚        |
| **联络员**                        | 对接学校管理员、上报监管的联系人(需有值班机制)     |

> 平时应指定**两个以上的应急值班联系人**(主+备),防止单点失联。联系表见附录 B。

## 4. 监测与报告流程

```
发现(技术告警 / 用户反馈 / 运维巡检 / 审计异常)
   │
   ├─ 先判真实性:是误报 / 配置错 / 真事件?
   │
   └─ 确认为真事件
        │
        ├─ 填写《安全事件快报》(附录 A)
        │
        ├─ 一级 → 技术处置组直接处置,24h 闭环,记录归档
        │
        ├─ 二级 → 上报应急总指挥 + 合规对接人,4h 内出初步结论
        │
        └─ 三级 → 立即全组响应,1h 内定级并准备监管通报
```

### 现有能力的监测抓手(务必启用)

- **access_logs(2B)**:敏感数据读取全留痕——异常批量读取(如某账号短时间内大量拉取学生列表/行权导出)是首要告警源
- **年度审计导出(2B)**:定期审计 access_logs,发现未授权读取模式
- **AI 出站审计(2D/2E/2F)**:AI 请求落库的 `is_ai/ai_meta` + 匿名化日志,排查 AI 出站是否携带敏感字段
- **行权记录(2B)**:教师/管理员代办查/导/改/删全部留痕,可溯源

## 5. 处置步骤(六步法)

### 5.1 隔离止损(技术处置组)

1. 立即撤回/作废疑似泄露的导出文件、密钥、URL
2. 冻结涉事账号的访问权限(禁用 token/会话,必要时停用账号)
3. 若为服务器/DB 层面问题:临时封禁异常 IP、断开可疑连接、缩小暴露面
4. **不要急于删数据/关服务**——先保全证据(见 5.3),再谈修复

### 5.2 定位根因

排查路径(按可能性排序):

- 前端直连 Supabase/后端接口的权限绕过(参考 2C 堵漏经验:曾存在前端直连 `exam_scores` 绕过鉴权)
- 行权导出(2B CSV)/学生列表接口的角色授权缺失(2F 已标注待分层脱敏)
- AI 出站携带敏感字段(2E/2F 已补漏,排查是否有历史遗留)
- 密钥/凭据泄露(本项目历史教训:打包产物曾泄露生产凭据,需一并核查轮换)
- 弱口令/撞库、钓鱼、供应链

### 5.3 证据保全

- 保存 access_logs、服务器日志、操作审计的**原始副本**(时间戳戳记)
- 记录:发现时间、涉及数据范围、可疑账号/IP/操作序列
- 涉及司法/监管可能介入的,交由合规对接人规范取证(勿自行破坏现场)

### 5.4 修复与加固

- 修复根因后**回归验证**(参考本项目 QA 惯例:前端 tsc/vitest + 后端 pytest 全量)
- 轮换受影响的密钥/凭据(凭据泄露类事件必须全量轮换,不可只换单点)
- 补齐缺失的控制(权限、脱敏、留痕),参照 2C/2E/2F 已建能力

### 5.5 通知义务(合规对接人)

按《个人信息保护法》第 57 条:

- **向监管报告**:通过履行个人信息保护职责的部门(网信部门)指定的渠道报告。报告要素:原因、危害、已采取措施、补救措施、联系人与联系电话
- **告知个人**:如泄露的个人信息可能危害个人权益(成绩/健康/家庭住址/监护信息),应通过电话/短信/站内信**告知受影响的家长/监护人**,说明泄露内容、风险、补救措施、可采取的自保建议
- 对未成年人敏感信息泄露,按从严口径执行

### 5.6 复盘与改进

- 事件复盘会:根因、处置时效、沟通有效性、流程缺口
- 输出改进项 → 纳入版本/批次计划(可参照本项目 feature-upgrade-plan 的批次机制)
- 更新本预案(版本递增,记录在「变更记录」)

## 6. 对外沟通

| 对象                  | 口径要点                                                                    |
| --------------------- | --------------------------------------------------------------------------- |
| **学校/老师(内部)**   | 事实 + 已采取措施 + 对教学影响(如有) + 后续安排;不揣测、不夸大              |
| **家长/监护人**       | 法定的告知义务(内容见 5.5);文案需合规对接人审定,统一出口,避免多部门口径不一 |
| **监管**              | 依法报告;由合规对接人统一对接                                               |
| **媒体/公众**(如涉及) | 原则上不自行对外发布;统一由负责人或公关口径,未经总指挥批准不得发声          |

---

## 7. 演练

- **至少每半年一次**桌面演练(三级事件模拟),覆盖:定级 → 上报 → 止损 → 通知 → 复盘
- 演练后 2 周内修订预案与实际不符之处
- 新员工(后端/运维/客服)入职须知晓本预案与值班联系人
